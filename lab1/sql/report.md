#### Бонус — операции-«сироты»

``
select count(*)
from raw.transactions tr
left join raw.cards c using(card_id)
where c.card_id is null
``
**Результат: 7 018**

Чем грозит?  Тихим занижением метрик оборота/количества операций, если их не обрабатывать явно.

## Часть 3. Три решения перед сборкой

**Зерно:** вариант *б*  - одна строка = одна уникальная операция (после удаления дублей), любого статуса; потому что только так можно ответить и на долю отклонённых, и на сумму трат клиентов (фильтром status = 'approved' уже на этапе аналитики, а не на входе).

**Р1.** declined и reversed остаются в факте - значит, каждый, кто пишет `sum(amount_rub)`, обязан фильтровать `where status = 'approved'`, иначе в сумму попадут неудавшиеся и отменённые операции ; 

**Р2.**    join rates on rates.date = дата_операции  INNER JOIN по точной дате, а в выходные курса нет, поэтому такие операции просто теряются; правильно будет ASOF JOIN, берущий курс последнего опубликованного дня не позже даты операции , так ни одна операция не пропадает.

**Вывод.** Цифры расходятся по двум причинам: во-первых, сырой запрос суммирует суммы как есть, а витрина сначала переводит валютные операции в рубли по курсу ЦБ -итоги выше; во-вторых, сырой запрос через INNER JOIN теряет операции-сироты, а витрина их не теряет - записывает на неопознанного клиента, поэтому у неё появляется лишняя строка «Не определён» на 17,2 млн ₽, которой в сыром результате нет вовсе.

## Финальный вопрос: выбор школы (Кимбалл / Инмон / Data Vault)

Я бы выбрала для компании подход **Кимбалла**, так как он быстрее строится и понятен аналитикам без BI-прослойки. Инмон требует сначала построить нормализованную модель предприятия целиком и только потом — витрины поверх неё, для компании это долгий старт без быстрого результата. Data Vault выигрывает в устойчивости к изменению источников и полной истории, но сложен сам по себе: нужно поддерживать три типа объектов вместо одной понятной звезды, и аналитикам всё равно нужен слой поверх него для отчётов.
